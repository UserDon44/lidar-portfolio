# LiDAR Bare-Earth DEM — Eastern Pima County, AZ

Portfolio deliverable: a bare-earth DEM built from raw LiDAR returns (not
the vendor's delivered classification), independently QC'd against the
vendor product, flight-line geometry, and the source collection's own
signed accuracy assessment. Produced as a work sample for survey and
geospatial firms in the Southwest — not a tutorial exercise.

**Bottom line:** the reprocessed surface agrees with the vendor's own
delivered ground classification to **0.162 ft RMSE**, clearing the ASPRS
QL2 non-vegetated accuracy threshold (≤0.328 ft) with margin. Full
writeup: [`output/reports/qc_report.pdf`](output/reports/qc_report.pdf)
(18 pages) or [`output/reports/qc_memo.md`](output/reports/qc_memo.md).

## Data source

[`USGS_LPC_Eastern_Pima_County_Lidar_980398.laz`](https://rockyweb.usgs.gov/vdelivery/Datasets/Staged/Elevation/LPC/Projects/Eastern_Pima_County_Lidar/AZ_Eastern_PimaCO_2015/LAZ/USGS_LPC_Eastern_Pima_County_Lidar_980398.laz)
— USGS 3DEP LiDAR Point Cloud, San Xavier District, Tohono O'odham Nation,
Pima County, AZ. 8,692,808 points, LAS 1.4 point format 6, 574 acres,
QL2 (~3.7 pts/m²). Flown Feb 20–26, 2015 by Sanborn Map Co. (Leica ALS70
HP), vertical datum NAVD88/Geoid12A — confirmed against the collection's
signed Psomas accuracy assessment, not the LAZ header (which declares
none). Horizontal: NAD83(2011) / Arizona Central, **International Feet**
(EPSG:6405) — not US survey feet, a real source of error this project
caught and fixed everywhere.

A second, steeper QL1 tile (Tucson Mountains / Wasson Peak vicinity) was
also processed with its own tuned parameters as a harder-terrain stress
test; its findings are documented separately (`docs/PROJECT_SUMMARY.md`,
`docs/session-log.md`), not in the primary QC memo above, which stays
scoped to the one tile.

## Pipeline

Raw returns → bare-earth DEM, no vendor classification used as an input
(only as a comparison baseline):

1. **ELM** (extended local minimum) — removes low outliers
2. **Statistical outlier removal**
3. **SMRF** ground classification (window 120 ft, slope 0.15, threshold
   1.6 ft — tuned per-tile, not left at metric defaults)
4. Ground points rasterized at 3 ft, IDW

`scripts/run_dem.py` runs a single parameter set; `scripts/batch_process.py`
runs every tile in `data/raw/` with per-tile tuned parameters
(`scripts/tile_params.json`). Every run's PDAL pipeline JSON is retained
in `scripts/pipelines/` as an audit trail.

## Key findings

- **Accuracy:** 0.162 ft RMSE vs. the vendor's delivered ground surface —
  clears ASPRS QL2 (≤0.328 ft).
- **Flight-line offset:** a systematic **~0.12 ft** vertical offset exists
  between two overlapping flight lines in the source collection — a real
  calibration artifact in the data, not a processing error, disclosed as
  a limitation.
- **Coverage:** tile-wide density meets the QL2 average (3.70 pts/m²), but
  **19.4% of cells** fall locally below the QL2 minimum — an average
  that passes can still hide local gaps.
- **Roof vs. pad:** crisp rectangular features in the residential block
  were investigated and resolved as graded concrete pads (+2.85 ft, not
  the 8–15 ft an unremoved roof would show), corroborated against current
  orthoimagery — a house now standing on the same footprint is consistent
  with construction sometime after the 2015 flight.
- **Beyond scope:** a full hydrologic-derivatives pass (depression
  fill/breach, flow routing, stream network, watershed) was also run —
  see `output/reports/qc_memo.md` §5.

## Reproduce it

```bash
conda activate lidar
python scripts/run_dem.py          # single-tile DEM build
python scripts/batch_process.py    # every tile in data/raw/
python scripts/render_figures.py   # regenerate all report figures
python scripts/build_report.py     # assemble qc_memo.md + figures -> PDF
```

Environment: conda env `lidar` (miniforge) — PDAL 2.10, GDAL 3.12, laspy,
rasterio, geopandas, WhiteboxTools. See `CLAUDE.md` for full environment
setup, including a real Windows PATH/DLL gotcha with unactivated shells.

`data/raw/` and most of `output/` are gitignored and regenerated by the
scripts above (`output/reports/` is the one tracked exception — it holds
hand-authored prose, not regenerable rasters).

## Known limitations

- No external vertical control point falls inside this specific tile —
  the collection's 134 check points are spread across the full ~2,203 sq
  mi project area. The project's own signed NVA (RMSEz 8.8 cm bare-earth
  DEM) is cited as the strongest available external accuracy evidence,
  but an in-tile check would require new fieldwork.
- Tile-boundary edge effects (SMRF ground classification degrades near a
  tile's edge) are not corrected for — this project has no pair of
  spatially-adjacent tiles to buffer from or test against.
- The derived stream network can't separate a real drainage channel from
  a center-pivot field's wheel-track ring by geometry alone; ag-area
  segments are flagged on the deliverable figure rather than
  threshold-tuned away.
- Full limitations list, with citations: `output/reports/qc_memo.md` §7.

## The automated number check was inert while this project was written

`.claude/hooks/check_deliverable_numbers.py` traces every number written
into `output/reports/` back to an artifact that derives it. **It never ran
as a hook.** Until 2026-08-12 it was invoked via its
`#!/usr/bin/env python3` shebang, which on this machine resolves to the
Windows Store stub — `"Python was not found"`, exit 49 — so the check was
configured and inert, and the companion `guard_destructive.py` silently
did not guard either.

The 2026-08-10 audit of every quantitative claim in these deliverables
was real and its corrections stand, but it was a **manual** run of that
script, not automatic per-write coverage. Recorded so nobody assumes
protection that was not operating. There is deliberately no
`last_number_audit.txt` here — had one existed it would have implied
coverage that never happened.

Fixed by invoking an explicit interpreter path, verified firing live.
